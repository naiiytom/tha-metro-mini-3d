## Implementation notes (learned in MVP 1 — read before touching the map/3D code)

- **Floating origin lives in `src/map/coordinates.ts`** — all Three geometry is built in a local east/north/up meter frame around Siam (`ORIGIN_LNG_LAT`); `ThreeLayer.ts` folds the float64 origin translation + mercator meter scale into the camera projection matrix each frame. Never put absolute mercator values into vertex data.
- **MapLibre's stylesheet forces `.maplibregl-map { position: relative }`**, overriding Tailwind's `absolute` on the container — size the map container with `h-full w-full`, not `absolute inset-0`, or it collapses to 0 height (silently: you get a 300px default canvas and a blank map).
- **Metric-width geometry disappears at low zoom.** The 9 m track deck is subpixel below ~z13, so each branch also gets a constant-pixel-width `Line2`/`LineMaterial` centerline (`buildTrackLine`); its `resolution` uniform must be updated per frame in `ThreeLayer.render()`.
- **Base map is OpenFreeMap's Liberty style** (`https://tiles.openfreemap.org/styles/liberty`) — vector tiles, free, no API key, includes 3D building extrusions that correctly depth-occlude the track.
- **Data provenance:** track geometry = OSM route relations 444651 (Sukhumvit) + 2067854 (Silom) via Overpass, ODbL; station coords = Namtang GTFS `route_id` 1 & 2, CC-BY 4.0. Both attributions render in the map's attribution control — keep them.
- **maplibre-gl is on v6.** The v4→v6 migration touched four things, all load-bearing: `render()` now takes `(gl, options)` and the mercator→clip matrix comes from `options.defaultProjectionData.mainMatrix`; there is **no default export** (named imports only); GL context flags moved from `MapOptions` into `canvasContextAttributes`; and v6 locates its tile worker via `new URL(\`./${name}\`, import.meta.url)` — a dynamic specifier no bundler can rewrite, so `MapContainer.tsx` must call `setWorkerUrl()` with a `?worker&url` import. **Without that call the base map goes silently blank** (style loads, tiles never parse) while the Three layer keeps drawing — so a screenshot that shows track but no buildings means the worker URL broke.
- **Camera input is custom** (`src/map/cameraControls.ts`) — it calls `map.dragRotate.disable()` and owns rotation entirely. Middle-drag, right-drag and ctrl+left-drag all **orbit**: vertical pitches, horizontal turns, applied together in one `jumpTo` so a diagonal drag does both. Directions and rates match MapLibre's (`-0.5 * dy`, `+0.8 * dx`); the reasons for replacing `dragRotate` rather than using it are that it has no middle-button binding and its rotation is anchored to the press point, so bearing response varies with where you clicked. Pan and scroll-zoom are left to MapLibre untouched. Verify with `npm run verify:camera`.
- **Click jitter can get misclassified as a drag.** MapLibre's default `clickTolerance` (3px) is how it tells a click from a drag-pan; ordinary pointer jitter between mousedown/mouseup can exceed that, firing `dragstart`. `MapContainer.tsx`'s `onDragStart` unconditionally drops `following` on any pan (so a real user drag hands control back — see `followCamera.ts`), so a misclassified click silently cancelled follow-camera on the very next click after engaging it. `MapContainer.tsx` sets `clickTolerance: 6` on the `MapLibreMap` constructor to absorb normal jitter; don't revert it as unused-looking noise. It's a mitigation, not a guarantee — a trackpad or touchscreen tap can still exceed 6px.

## Implementation notes (learned in MVP 2/3 — engine & pipeline)

- **`docs/ENGINE_CONTRACT.md` is the interface spec** for the cache format, stride-8 `Float32Array` vehicle buffer, worker protocol, and wasm API. Update it when any of those change — it's what keeps the Rust and TS sides in sync.
- **The Namtang feed is frequency-based for BTS**: routes 1/2 have 14 trip *patterns* with relative `stop_times` (starting 00:00:00) expanded via `frequencies.txt` headway windows (06:00–24:00). The preprocessor (`rust-engine/preprocessor`) expands them into ~2,162 concrete runs. Service 1 = weekdays, 2 = weekends, with 42 Thai-holiday `calendar_dates` exceptions.
- **MapLibre's earth radius is 6371008.8 m** (`src/geo/lng_lat.ts`), NOT the WGS84 circumference — `sim-core/src/geo.rs` replicates MapLibre's exact math so Rust ENU output matches `src/map/coordinates.ts` to sub-millimeter (unit-tested). Don't "fix" it to 40075016.686.
- **Engine positions are a pure function of time** (no integration): worker evaluates at 10 Hz into pooled transferable buffers (3-buffer ping-pong, never allocates on the frame path); `SimClient.getInterpolated` lerps the two latest frames matched by `run_idx`. Per-frame data never touches React/Zustand.
- **Schedule metadata is engine-side, not TS-side** (`sim-core/src/query.rs`, contract §7). The vehicle buffer carries pose only; headsign/ETA/origin/destination/station boards come from `run_detail`/`station_board` over a promise-based worker query channel. They are UI-rate (on selection, ~1 Hz) — putting one on the frame path re-introduces exactly the boundary cost §3A.2 exists to avoid. The TS mirrors in `protocol.ts` keep serde's snake_case verbatim; rename a field in Rust and the UI breaks silently unless both move together.
- **Trains are one draw call per route**: one merged vertex-colored geometry per route in `VehicleManager` (InstancedMesh, capacity `MAX_VEHICLES` = 1024 as of MVP 5 — was 512 through MVP 2–4, raised ahead of the 9-line network so a real peak is never silently truncated). That was "2 draw calls total" when the network was Green Line only (Sukhumvit + Silom); it is N draw calls for an N-line network now — still one per route, never one per train (SRS §3A.5).
- Bangkok time = UTC+7 fixed (no DST); the worker splits `simEpochMs + 7 h` into `date_yyyymmdd` + `sec_of_day` via UTC getters, and the engine also evaluates the *previous* service day at `sec+86400` for post-midnight spillover.
- Kheha (stop 13608) snaps 63.9 m from the OSM track end — still a genuine terminus geometry offset, still under the 150 m hard limit, but **no longer the network's largest snap** now that the full 10-line network is in. The committed `public/data/network.report.json`'s `max_snap_m` (109.47 m) belongs to **MRT Itsaraphap, GTFS stop_id `13627`, MRT Blue Line** — confirmed from the preprocessor's own stderr, not a nearest-point re-derivation (finding 8, PR #8 review). The old claim that "every other stop snaps < 40 m" was stale and wrong: five stops exceed 40 m today — Itsaraphap 109.5 m, Kheha 63.9 m, Chatuchak Park (Blue) 61.1 m, Queen Sirikit NCC (Blue) 48.9 m, and Krung Thep Aphiwat (SRT Light Red) 44.3 m — all still comfortably under the 150 m hard limit. Blue accounts for three of the five; a denser, more convoluted underground alignment snapping worse than the elevated BTS lines it was benchmarked against is the expected shape, not a red flag.

## Implementation notes (learned in MVP 5 — multi-line breadth)

- **The registry-index invariant is the load-bearing contract of the whole line-agnostic pipeline.** `tools/lines.config.mjs`'s `LINES` array order == `src/data/network.json` `lines[i]` order == the Rust cache's `CacheDoc.routes[i]` order == vehicle-buffer `route_idx` (lane 6) == `VehicleManager`'s per-route `InstancedMesh` index. It is enforced at three independent points: `assertRegistryValid()` (duplicate keys/route-ids, unknown structure/vehicleType, malformed color/id-list fields), a Rust preprocessor test (`route_order_follows_network_json_line_order`), and the fact that nothing anywhere hardcodes a route index or name — `fetch-network.mjs`, the preprocessor, and the frontend all just iterate whatever `LINES`/`network.json` contains. Appending a line is safe; reordering or removing one invalidates every committed `.tmb` and desyncs `route_idx` across the whole stack.
- **The track-only route path (`gtfsRouteId: null`) is a real, tested mechanism, not a stub.** A line entry with no GTFS route id renders (track + stations from its own `network.json` data) but never simulates (`RouteDoc.simulated = false`, no patterns, no runs, `station_board`/`run_detail` return an empty board rather than erroring — see `sim-core/src/query.rs` tests `a_track_only_route_has_an_empty_board_not_a_missing_one` / `..._still_reports_its_stations`). **No line in the current registry actually uses it** — all 9 entries in `LINES` have a real `gtfsRouteId` and are fully simulated; MRT Orange (the intended first user of this path) isn't in the registry at all yet, deferred whole to MVP 6. Don't read "9 lines rendered" as "9 lines simulated, plus track-only ones" — right now those are the same 9.
- **Interchange metadata is auto-linked within 300 m, plus a manual override list for what that radius can't reach.** The preprocessor's `link_interchanges()` (called with `INTERCHANGE_RADIUS_M = 300.0`) pairs any two different routes' stations within 300 m of each other, symmetric, never self-referential. `INTERCHANGE_OVERRIDES` in `tools/lines.config.mjs` (fed through as `TrackFile.interchange_overrides`, GTFS stop-id pairs) covers walkways/platforms the radius genuinely can't see — currently one entry: Purple↔Pink at Nonthaburi Civic Center, whose two platforms are ~555 m apart but share the same GTFS `stop_id` "359" on both sides (verified against OSM node tags, see the long comment on the `pink` registry entry), so the override pairs `["359", "359"]` — safe because no other route uses that stop id, so it can only ever resolve to Purple's copy and Pink's copy of it.
- **A registry line's `gtfsRouteId: Some(id)` doesn't guarantee frequency-based expansion.** The Namtang feed mixes both GTFS shapes: BTS-style routes (Sukhumvit, Silom) are frequency-based (relative `stop_times` + `frequencies.txt` headway windows); other operators (ARL, SRT Red, etc.) publish concrete absolute departures with no `frequencies.txt` rows for their trips at all. `runs_for_pattern()` in the preprocessor handles both: a trip with frequency rows expands into one run per headway slot, a trip with none becomes exactly one run starting at its own first stop's arrival time. A trip with neither shape is a hard error, never a silent zero-run drop.
- **`window.__map.getLayer("network-3d")` does not hand back the `NetworkLayer` instance directly.** MapLibre wraps every added layer in its own style-layer object; the `CustomLayerInterface` you passed to `addLayer()` — and its Three `scene` — lives on `.implementation`. Needed this to reach real rendered `InstancedMesh` geometry from a verify script (`tools/verify-mvp5.mjs`) rather than trusting the `ConsistSpec` config table alone.
- **`StationBoard.tsx`'s "Interchange" label and its transfer chips render inside a `uppercase`-styled heading** — `document.body.innerText` reflects the CSS text-transform, so a verify script comparing against the literal string `"Interchange"` (mixed case) silently never matches; compare case-insensitively, same gotcha `verify-mvp4.mjs` already documents for "next departures".

## Implementation notes (learned in MVP 6 — underground + polish)

- **Per-point structure comes from a two-query Overpass fetch, not the one-query `out geom` the earlier MVPs used.** A relation's `out geom` response does not carry tags on member ways, so `tools/fetch-network.mjs` now fetches each relation twice: `out geom` for the polyline itself, then a second `way(id:<ids>); out tags;` query to get `bridge`/`tunnel`/`layer`/`embankment`/`covered` for the `structureOfWay` classifier (mirrored in `src/map/structure.ts` and `tools/lines.config.mjs`, cross-checked against drift by `src/map/structure.crosscheck.test.ts`). A registry line's `structure` field is now the *fallback* for an untagged way, not one nominal altitude for the whole line — and that fallback default genuinely differs by line: SRT Dark/Light Red default to `"atGrade"` (their untagged/embankment ways really are at grade), every other line still defaults to `"elevated"`.
- **`tunnel=building_passage` is NOT underground.** SRT Dark/Light Red cross Bang Sue Grand Station on a way tagged `tunnel=building_passage` + `layer=1` + `covered=yes` — on elevated viaduct, not in a tunnel. Real Bangkok OSM data contradicted the original plan's assumption; the classifier special-cases this tag explicitly rather than treating any non-`no` `tunnel` value as underground.
- **MRT Blue's alignment passes near itself at Tha Phra** (the Bang Sue loop joins the Bang Wa/Lak Song branch there), so a single stop can legitimately sit near the polyline at two different arc positions. The original global-nearest-point stop snapping picked whichever pass happened to be closer, independent of which pattern was asking — for Tha Phra that put two physically-adjacent stations 38,290 m apart in **arc-length** (1,226 m apart in real space), so a scheduled leg between them interpolated as a ~38 km sweep across the map in a 120 s window. Fixed with **per-pattern monotonic stop snapping** in the preprocessor (`rust-engine/preprocessor/src/spline.rs`'s `snap_candidates` + `main.rs`'s `resolve_pattern_arcs`): direction is decided once per pattern by trend-voting across every consecutive stop pair, then a single constrained walk assigns each stop the nearest candidate consistent with the running arc. **The polyline is NOT closed** (its two ends are ~7.3 km apart in real space) — "wrap arc-length modulo total length" is not a valid fix for this, only the per-pattern walk is.
- **`INTERCHANGE_OVERRIDES` edits in `tools/lines.config.mjs` do nothing on their own.** The preprocessor reads overrides from `network.json`'s own `interchangeOverrides` copy (`rust-engine/preprocessor/src/main.rs`), not from the registry directly — only `tools/fetch-network.mjs` copies the registry array into that file. Editing the registry and re-running the preprocessor without a re-fetch silently no-ops, with every step still reporting success. Either re-fetch or hand-sync `network.json`'s copy after an override edit. This cost a full debug cycle in MVP 6 (two new overrides — Silom↔Blue at Sala Daeng/Si Lom, 319.3 m; ARL↔Blue at Makkasan/Phetchaburi, 304.8 m — both genuinely just outside the 300 m auto-link radius).
- **The underground view mode is opacity-based, not depth-correct — say so plainly, don't call it "underground transparency" and let a reader assume real occlusion.** `NetworkLayer.applyUndergroundMode()` (`src/map/ThreeLayer.ts`) makes sub-surface track translucent and stops writing depth for it when the mode is off; MapLibre's own `fill`/`fill-extrusion` layers get dimmed to 0.25 opacity (inside SRS F3.2's 0.1–0.4 band) when the mode is on. There is **no real depth-buffer interop** between MapLibre's tiles and the Three.js layer — the code's own comment states the tradeoff directly: sub-surface geometry "does not write depth... reads as beneath without needing real depth interop with MapLibre's tiles (§3A.4 — that is the open-ended problem this deliberately sidesteps)." From some camera angles sub-surface geometry can still draw over buildings that should occlude it. This is the accepted, disclosed cost of skipping §3A.4's harder depth-interop path — not a bug to chase.
- **Underground opacity (Task 7) and basemap day/night colour (Task 10b) both touch MapLibre paint properties on the same layers and must stay strictly separated.** Task 7 owns every `*-opacity` property; Task 10b owns colour properties (`background-color`/`fill-color`/`fill-extrusion-color`/`line-color`/`text-color`/`text-halo-color`) only — if either wrote the other's property they would clobber each other every ~2 Hz tick. Task 10b also must always blend from each layer's colour as **captured once at `style.load`**, never from the layer's live value: blending from the live value compounds every tick and drives the whole map to black within seconds. (This shipped as a real bug in the first Task 10b pass — the night factor was applied twice, once inside a `basemapTheme()` helper and again in `MapContainer.tsx` — and was caught and fixed; the fixed version blends `entry.original -> NIGHT_THEME[role]` directly, once, per tick.)
- **Shadow toggle, measured cost (default off) — and core-only coverage, not network-wide.** `shadowsEnabled` flips `renderer.shadowMap.enabled` (PCFSoftShadowMap, 2048² map, a tightly-fit 4 km orthographic frustum fixed around Siam — `ThreeLayer.ts`'s own comment on this is accurate). The network spans ~50 km, so panning out to e.g. Rangsit or Lak Song puts you well outside the frustum and shadows silently stop rendering there even with the toggle on; this is a real, accepted limitation of a "tightly-fit" shadow box (widening it would quantise the shadow map into uselessness instead), not a bug — but the toggle's own UI label didn't say so until finding 6d's review pass (`ViewControls.tsx`'s "Shadows" row hint now does). Measured against a real production build (headless Edge + `--enable-unsafe-swiftshader` **software** rendering — not real GPU hardware, so treat the absolute milliseconds as illustrative, not a hardware benchmark) at the network's daily peak minute: enabling shadows roughly **doubled** the mean cost of the Three.js `renderer.render()` call itself across two independent runs (0.46 ms → 0.94 ms, then 0.70 ms → 1.15 ms; p95 rose similarly, e.g. 0.60 ms → 1.30 ms). End-to-end `requestAnimationFrame` rate stayed pinned at ~100 FPS in both configurations in this environment — that ceiling is this headless/software-rendering setup's own cap (it matches `verify:perf`'s own ~100 FPS figure), not proof shadows are free; it means this environment's FPS counter can't distinguish the two settings, but the render-call timing above shows the real, measurable per-frame cost. No regression below the 55 FPS `verify:perf` gate was observed with shadows on.
- **`TMB_VERSION` bumped 2 → 3** (MVP 6 Task 1, landed before Task 5's data work): `InterchangeRef.route_idx` widened `u8` → `u16`, because an unchecked `u8` would silently wrap once a network exceeds 256 routes — not a risk at today's 10, but a real class of future bug this closes for good. `rust-engine/sim-core/src/model.rs`'s own `CacheDoc.version` field still has a stale `// 2` comment next to the `u16` value `3` — a known, already-deferred minor finding (recorded in the MVP 6 ledger), not fixed here since this is a docs-only pass and that file is source, not documentation.
- **The `preRevenue` line-rendering mechanism had no real user through the end of MVP 6 itself, same shape as MVP 5's track-only-route note below.** Task 4 built and unit-tested it fully — dashed centerline, desaturated/translucent deck, registry validation that refuses a `preRevenue` line with a non-null `gtfsRouteId`, and a `LineSelector` badge — but its intended first consumer (MRT Orange / Purple Phase 2, Task 6) was deferred within the MVP 6 cycle. It got real users once Task 6 was picked back up (2026-08-04, see "Orange/Purple Phase 2 track-only fetch" further down): `grep -c 'preRevenue: true' tools/lines.config.mjs` is now **2**, not 0. `npm run verify:mvp6`'s original brief included two checks for this mechanism (a pre-revenue line renders but never simulates; a pre-revenue station's board resolves empty, not an error) — both were left out of the MVP 6 harness because they'd have asserted `0 >= 2` against the then-real registry, replaced at the time with two checks that asserted what MVP 6 actually shipped (MRT Blue's split deck meshes; the basemap darkening at night). Now that Task 6 has landed, the original two checks belong back in the harness — see the Orange/Purple Phase 2 notes for whether that's been done.
- **Mo Chit (BTS N8) is a real, tagged OSM station node now — it was not always one.** It was absent from the OSM fetch that produced `network.json` at commit `4bf22da`, and the original hand patch (commit `ef339e9`) cited OSM node `270666807` as its position — that node is **untagged** (a plain way node, not a station) and sits ~270 m from the coordinate it was used to justify, a citation that never actually supported its own value. `b4c1cb9` (Task 13, a user-reported "Mo Chit looks wrong" defect) replaced it with the real station node **`5388599065`** (`railway=station`, `public_transport=station`, `ref=N8`, `name:en=Mo Chit`, operator BTSC, `wikidata=Q873641`, and a genuine member of both the current BTS Sukhumvit route relation `7989376` and stop_area relation `2108262`) at **13.8025991, 100.5537913** — a ~270 m move that improved its track-snap from **187.4 m to 2.2 m**. **A re-fetch would not have fixed this on its own**: Task 13 independently re-confirmed the pinned relation `444651` still does not contain Mo Chit at all, so the station still needs the hand-patch mechanism — what changed is which coordinate/id that patch cites, not whether a patch is needed. A side effect of the wrong position, invisible until Task 13: Mo Chit's simulated `StationDoc.code` was silently blank (the preprocessor's 100 m enrichment fallback couldn't match GTFS stop 37 at 187 m); it now correctly resolves to `"N8"`.
  > **Stale as of this paragraph — corrected 2026-08-05 (MVP 7).** This whole hand-patch is no longer reflected in the currently-committed `src/data/network.json`: `grep -c "Mo Chit" src/data/network.json` returns **0** — the station is entirely absent, not just mispositioned. This is a pre-existing regression from before MVP 7 (a later full re-fetch, `333b799`, silently dropped it — confirmed identical at both the base and head of MVP 7's own Task 2, so MVP 7 did not introduce it and did not fix it either). No snap-distance gate, old or new, can catch a MISSING station entry — only a wrong-but-present one. Flagged here for the human partner rather than fixed in this pass: fixing the underlying missing-station data needs its own investigation (why the later re-fetch dropped it, and re-applying an equivalent hand patch against current data), out of scope for a docs-accuracy task.
- **Track altitude is gradient-limited, not a per-point step function.** `STRUCTURE_ALTITUDE_M` (in `tools/lines.config.mjs`) still assigns each track point its band's nominal altitude, but that step function alone produced up to a **108% grade** at a structure-tag transition (red-dark idx 103: +14.5 m over just 13.4 m of track) — a near-vertical wall, made worse by Catmull-Rom overshoot, which is what a user reported as "huge gaps" at portals (a real user-reported visual defect, fixed in `b4c1cb9`, Task 13). `tools/trackProfile.mjs`'s `limitTrackGradient` (`MAX_TRACK_GRADIENT = 0.04`, the standard heavy-rail ruling gradient) is a two-sided forward/backward relaxation sweep over cumulative along-track (haversine) distance that caps the altitude delta between consecutive points to 4% of their separation. After the fix, the worst gradient anywhere in the whole network is exactly **4.00%** (blue idx 347) — every other transition is at or under that cap, and **deep-run interior altitudes are preserved exactly** (e.g. Blue's underground interior is still byte-identical at −18 m far from any portal). **Only the altitude channel (index 2) moves — lon/lat and the structure tag (index 3) are untouched.** That has a load-bearing subtlety: a point tagged `underground` can legitimately sit well above nominal −18 m mid-ramp (it's on the ramp, not yet at depth), and Task 7's underground-view mode sorts rendered geometry by *tag*, not by altitude — so a mid-ramp point renders in its tag's band (translucent/depth-unwritten if `underground`) even where it visually reads as near the surface. It's applied both in the pipeline (`tools/fetch-network.mjs`'s `fetchBranch`) and, deterministically, to the already-committed `network.json` (no re-fetch was run) — same precedent as `preRevenue` and `interchangeOverrides`: a future real `data:fetch` reproduces the same ramped altitudes as a no-op diff. Station altitude resampling piggybacks on this narrowly: a station only gets resampled off the ramped track (via `nearestTrackAltitude`) if its single nearest track vertex was itself among the points the limiter actually moved — see the "known gaps" note below for that heuristic's boundary case.
- **Night lighting has a raised floor so the network stays readable after dark**, fixed in `0b9a921` (Task 14, a second user-reported defect: "the night theme make all the line invisible/hard to see"). `src/map/sun.ts`'s `skyPalette()` night floors moved `sunIntensity` 0.15→0.9 and `ambientIntensity` 0.55→1.35; the day-side lerp endpoints (2.2 / 1.6) are untouched, so noon output is byte-identical to before. The Three.js scene contains *only* network geometry (track/stations/vehicles, all `MeshLambertMaterial`) — no basemap — so raising this floor brightens the network without touching Task 10b's independent basemap night-darkening at all; the two were compounding before this fix (every material's rendered colour is roughly `color * (ambient + diffuse)`, so a dark line colour like Blue's `#1964B7` rendered near-black against an already-dark basemap). Worth recording *why* this isn't as flat a fix as the raw intensity ratios (0.9/2.2 ≈ 41%, 1.35/1.6 ≈ 84%) suggest: `NIGHT_AMBIENT` (`0x2c3a55`) and `NIGHT_SUN` (`0x3d5a8a`) are dark navy/blue, not white, so the real per-channel night/noon contrast (color × intensity, verified by direct computation) is roughly **10–28%** depending on channel (sun: R 9.8%, G 14.4%, B 22.1%; ambient: R 14.6%, G 19.2%, B 28.1%) — narrower than the raw intensity ratios imply. `ThreeLayer.ts:129`'s `Math.max(dir.up, 0.05)` floor additionally forces a grazing (never fully horizontal) sun angle at night, which is what keeps the directional term from going fully flat. **No automated check asserts night legibility** — `sun.test.ts` only pins the two numeric floors and their ordering relative to noon; whether the result actually *reads* as legible rests on visual screenshot inspection (see Task 14's report), not a gate.
- **All three of the defects above (Mo Chit, the gradient walls, and night legibility) were found by a human looking at the running app, not by any automated gate.** `npm run verify:mvp6`, `npm run verify:kinematics`, and the full unit suite were all green throughout both fixes — none of them assert anything about visual smoothness or visual legibility, only data-shape/numeric invariants. That's a real coverage gap, not a one-off. Worth naming for whoever plans MVP 7:
  - A **machine-checkable night-legibility assertion** (e.g. an offscreen render + luminance readback of track/vehicle pixels at two clock times, midday vs. deep night, asserting a minimum contrast against the basemap) would close the biggest part of this gap — it's the one of the three defects with no numeric proxy today.
  - The **`onRamp` station-resampling heuristic** (`tools/fetch-network.mjs`, `fetchBranch`) uses only the single nearest track vertex's before/after altitude (`nearestTrackAltitude` + a raw-vs-ramped comparison at that one index) to decide whether a station should be resampled. A station that is geometrically inside a ramp zone but whose *single nearest* vertex happens to fall just outside the set of points the limiter actually moved would keep its stale nominal altitude — a false negative. No such case exists in the current network (checked and reported in Task 13), and the narrow scoping is deliberate (a blanket resample would silently mask a separate, larger, undocumented-elsewhere issue: every station on a mixed-structure line defaults to its line's one nominal altitude regardless of local structure — real, but explicitly out of Task 13's scope). Record this as a known boundary, not a bug to fix reflexively.
  - `tools/trackProfile.mjs`'s `limitTrackGradient` bounds its relaxation sweep at `maxIterations = points.length + 2` — an O(n²) worst case that real track data never exercises (every line converges in 1–2 passes; the bound exists only as a safety net) and that logs nothing if it were ever actually hit, so a pathological future input (e.g. many alternating short structure "bumps" in sequence) could silently degrade preprocessing time with no visible signal.

## Implementation notes (mobile responsive pass + on-map train tooltip)

Two independent changes landed together (post-MVP 6, not yet folded into a numbered MVP): a mobile/touch-friendly responsive layout below Tailwind's `md:` (768px) breakpoint, and a DOM-owned on-map label that tracks the selected train's screen position.

- **`src/hooks/` is a new top-level directory**, not listed in SRS §6's project structure (`hooks/useIsMobile.ts`). It holds the one `md:` breakpoint media-query hook every mobile/desktop JSX split depends on (`MOBILE_BREAKPOINT_QUERY = "(max-width: 767px)"`, exported specifically so it can be pinned against Tailwind's 768px number in a test without a DOM).
- **The on-map train tooltip (`src/map/trainTooltip.ts`) is deliberately not a React component**, for the same reason `FollowCamera` (`followCamera.ts`) isn't: its position updates every frame, and per-frame data must never go through React/Zustand (§3A.7). It follows the exact same `capture()`/`apply()` split — `capture()` runs inside the layer's render pass and only reads a position; `apply()` runs in the rAF loop and is the only place that touches the DOM. Content (headsign/next-stop text) is UI-rate, set via a plain 1 Hz poll in `MapContainer.tsx` mirroring `TrainInspector.tsx`'s own poll — including the same "only reset the placeholder on a selection change, never on every poll tick" rule `TrainInspector.tsx`'s effect already followed; writing it unconditionally on every tick briefly flashed resolved content back to `Train {idx}` once a second.
- **Being DOM-owned means the tooltip doesn't inherit React-driven visibility for free.** The mobile "hide UI" toggle (`uiHidden` in the store) collapses every React-rendered overlay by CSS, but has no effect on an element `MapContainer.tsx` manages directly — `TrainTooltip.apply()` takes `uiHidden` as a second argument specifically so "hide UI" actually hides it too, rather than leaving an on-map label up under a control that claims to collapse "every overlay."
- **The `pixelRatio` cap (`Math.min(devicePixelRatio, 2)` on the shared MapLibre/Three canvas) is gated on `matchMedia("(pointer: coarse)")`**, not applied unconditionally. It exists to bound fragment cost on high-DPI phones; applying it on desktop too was a real, measurable sharpness regression on 3x desktop displays that were never the problem it was solving.
- **`LineSelector`'s expanded card reserves room for the bottom sheet stack** (`max-h-[calc(100dvh-16rem)]` below `md:`, vs. the desktop `calc(100dvh-2rem)`) rather than only checking it doesn't overlap `NavigationControl`. At small phone viewports the fully expanded card (header + 10 line rows + `ViewControls`) is tall enough to run into the always-present `TimeScrubber`/`TimeControls` stack (which renders once the engine is ready regardless of whether anything is selected) if given the same headroom desktop gets; it now scrolls internally (it already had `overflow-y-auto`) instead of overlapping.
- **`tools/verify-mobile.mjs` and `tools/verify-train-tooltip.mjs` select on `data-testid` attributes** (`line-selector`, `train-inspector`, `time-scrubber`, `bottom-sheet-stack`, plus the tooltip's pre-existing `train-tooltip`), not Tailwind class strings. The class-string selectors these scripts started with (`.absolute.left-4.top-4`, `.rounded-t-2xl`, `` input[type="range"]`.closest(".pointer-events-none")` ``) broke silently the moment `LineSelector`'s `left-4` became a safe-area-aware arbitrary value in the same change — the exact fragility a `data-testid` was meant to avoid.
- **`tools/verify-mobile.mjs`'s `devicePixelRatio` check runs at `deviceScaleFactor: 3`, not the page's default 2.** At `deviceScaleFactor: 2`, `Math.min(devicePixelRatio, 2)` and an uncapped `devicePixelRatio` are indistinguishable (`Math.min(2, 2) === 2` either way) — the check needs a scale factor above the cap to actually exercise it.
- **A real single-finger touch drag now pans the map in `verify-mobile.mjs`** (`page.touchscreen.touchStart`/`touchMove`/`touchEnd`), rather than only asserting from `cameraControls.ts`'s source that touch gestures fall through to MapLibre's own handling. The custom orbit controller only binds mouse-button + modifier-key drags, so this exercises the actual fallback path rather than trusting the claim.

## Implementation notes (Orange/Purple Phase 2 track-only fetch, 2026-08-04)

MVP 6's Task 6 assumed a route relation would exist for MRT Orange and MRT Purple Phase 2, the same shape every other registry line uses. That assumption was checked and found false, which changed the mechanism actually needed:

- **Neither line has a `type=route` relation anywhere in OSM's Bangkok data.** Checked operational (`route=subway`/`train`/etc.), `route=construction`, and `proposed:route` — all empty, for both lines, verified 2026-08-04. `discoverRelationId`'s widened construction/proposed query (already present in `fetch-network.mjs` from MVP 6 planning) is correct; there is simply nothing for it to find yet. What *does* exist: real, individually-tagged `railway=construction` ways — 16-17 for Orange (name exactly `รถไฟฟ้ามหานคร สายสีส้ม`, deliberately excluding the separately-named "...ตะวันตก" (West) ways per the original plan's Eastern-Section-only scoping), 10 for Purple Phase 2 (`รถไฟฟ้าสายสีม่วงใต้ ช่วงเตาปูน–ราษฎร์บูรณะ-ครุใน`) — with genuine `tunnel`/`bridge`/`layer` tags, so per-point structure classification works exactly as it does for every other line.
- **A new fetch path, `fetchBranchFromWayName(namePattern, branchKey, defaultStructure)` in `tools/fetch-network.mjs`, queries these ways directly and stitches them, bypassing the relation layer entirely.** Dispatched in `main()` off a new registry field, `osm.wayNamePattern` (mutually exclusive with `osm.relationId`/`osm.match`) — a line with this field set skips `fetchBranch`/`discoverRelationId` completely. Two things a relation-based fetch gets for free that this path has to do itself: (1) a standalone way's `out geom` response already carries its own tags, unlike a relation member list, so no follow-up tags query is needed; (2) **ways tagged `service` (crossover/siding/spur — pocket track between the two running tracks) must be filtered out before stitching**, or the greedy nearest-endpoint stitcher can walk onto a dead-end pocket track instead of following the main alignment. A real PTv2 route relation would never include these as members; a raw name-based way query has no such filter built in.
- **Both lines have zero stations, deliberately.** A citywide Overpass search for construction-stage station nodes (`construction=station`, `public_transport=construction`) found exactly 2 in all of OSM — and both fall **outside** the bounding box of these two lines' own fetched track ways, meaning they're either on a section not fetched here or a mistagged/unrelated node reusing a station name. Neither is trustworthy enough to place on the map (same standing practice as the Mo Chit/Itsaraphap snap fixes above: verify a position before committing it, never guess from a name alone). `fetchBranchFromWayName` always returns `stations: []`. The `preRevenue` mechanism (dashed centerline, desaturated deck) doesn't need stations to work — it renders correctly off track geometry alone.
- **A way-name-based fetch has no relation-level direction, and the first version of this shipped a real bug because of it: MRT Orange's stitched polyline was an out-and-back double-track loop, caught in code review, not before.** Two nearly-parallel construction-tagged tracks (up/down, no direction tag distinguishing them) greedily stitched end-to-end into one 43.6 km polyline for a real ~22 km alignment — walk out on one track, U-turn at the Min Buri end, walk back ~30 m away on the other. `length_m` was ~2× reality and the rendered deck drew twice with a visible U-turn. `purple-ext` didn't have this problem (its OSM mapping is a single clean traverse) — the failure mode is per-line OSM-mapping-dependent, not universal. Fixed with `truncateAtFold` (`tools/trackProfile.mjs`): detects a SUSTAINED run of points bending back close to the path's own earlier trace (not a single coincidence — real self-proximity, like MRT Blue's loop-plus-branch at Tha Phra, must not false-positive), then refines backward to the true local-maximum-distance turnaround and cuts there. Fixed Orange: 21.8 km, 171 points (88 underground/83 elevated), single traverse. `stitchWays` also now reports `{ path, consumed, total }` instead of just the path, and both `fetchBranch` and `fetchBranchFromWayName` warn when a candidate way didn't make it into the stitched result (previously silent — the way-based path's own log line reported ways *queried*, not ways *actually stitched*, which would have read as success even with 6 of 16 ways silently dropped). Both `stitchWays`/`truncateAtFold` live in `trackProfile.mjs`, not inline in `fetch-network.mjs`, specifically so they're unit-testable with synthetic fixtures (`trackProfile.test.mjs`) rather than only exercisable via a live Overpass fetch.
- **The Namtang GTFS feed isn't committed to the repo and wasn't before this change either** — it's ~230 MB extracted (dominated by `shapes.txt` at 155 MB and `fare_attributes.txt`/`fare_rules.txt` at 65 MB combined, neither read by the preprocessor), fetched fresh from `https://namtang-api.otp.go.th/download/namtang-gtfs.zip` (CC-BY 4.0) each time. What's new: `npm run data:fetch-gtfs` (`tools/fetch-gtfs.mjs`) automates the download+extract into a gitignored `.gtfs-cache/`, replacing what used to be a manual curl+unzip; the downloaded zip is written under `os.tmpdir()`, never into the repo tree, so an interrupted extraction can't leave a stray archive for `git status` to notice. `npm run data:preprocess -- --gtfs .gtfs-cache` picks it up. Orange/Purple Phase 2 themselves don't actually need GTFS data (`gtfsRouteId: null`, so the preprocessor emits `patterns: 0, runs: 0` for both regardless) — the preprocessor still needs *a* GTFS directory argument to run at all, since the other 10 lines share the one pass. Re-fetching the feed during this work picked up a newer snapshot than `main`'s committed cache (`feed_version` 20260801 → 20260803) — every per-route `runs`/`stations`/`length_m` is byte-identical except the two new lines, but one station label changed as a result: Mo Chit's interchange entry reads "BTS Mo Chit" instead of "Mo Chit".
- **Registry impact:** `LINES` grew from 10 to 12 (`orange`, `purple-ext` appended — append-only, same invariant as always). Network totals are unchanged (8,193 runs, 193 stations) since both new lines contribute zero of either. `npm run check:bundle` is 1.01 MB gzip (up from MVP 6's 0.96 MB, still 5 MB budget) from the added track geometry.

## Implementation notes (learned in MVP 7 — guardrails & presentation, 2026-08-05)

MVP 7 was not on the SRS's original ladder — it is a post-v1.0-DoD hardening pass (`docs/superpowers/plans/2026-08-04-mvp7-guardrails-and-presentation.md`), closing the automated-coverage gap MVP 6 exposed and delivering the addition-roadmap's remaining trivial/medium UI items. It shipped 13 tasks (12 from the plan file — `## Task 1:` through `## Task 12:` in `docs/superpowers/plans/2026-08-04-mvp7-guardrails-and-presentation.md` — plus one ad-hoc mid-plan request not in that file, the Orange East+West merge, see the correction note above). Registry stayed at **12 lines** throughout (10 simulated + `orange`/`purple-ext` track-only) — do not read "MVP 7" as having changed that count.

- **`styleBinding.ts`'s per-style/per-map split, and why re-creating `SimClient` on a style swap would be a real leak.** `map.setStyle()` (needed for the basemap style cycle, roadmap item 21) destroys every custom layer, including the Three.js `network-3d` scene — but `SimClient` (the worker + the timetable cache it holds), `FollowCamera`, `TrainTooltip`, the click/drag handlers, and the rAF loop must all survive a swap untouched, because they are per-**map**, not per-**style**. `src/map/styleBinding.ts`'s `bindStyle()` isolates exactly the two things that ARE per-style (the underground-opacity snapshot, the basemap-colour snapshot) into a fresh object built fresh on every `style.load`; `MapContainer.tsx` hoists `layer`/`vehicleManager`/`binding` as closure variables re-assigned each swap, guarded by a `simInitialised` flag so `SimClient` is constructed exactly once per mount. Creating a second `SimClient` on a swap would spawn a second Web Worker holding a second copy of the ~370 KB binary timetable cache — a real, silent resource leak, not just redundant work. A real bug was found and fixed while building this (Task 6): MapLibre v6's diffed `setStyle()` never sees custom layers at all (`Style.serialize()` explicitly excludes `type: "custom"`, `CustomStyleLayer.serialize()` even throws if called), so the OLD `NetworkLayer` instance silently survived a swap and the new `style.load`'s `map.addLayer()` collided with "Layer ... already exists." `{diff: false}` looked like a fix but is worse — it tears down the whole `Style` object without ever calling `removeLayer()` per layer, so `NetworkLayer.onRemove()` (which disposes real Three.js geometry/materials/the renderer wrapper) never fires, leaking GPU resources on every swap instead. The actual fix: explicitly `map.removeLayer(layer.id)` before `setStyle()`, which runs the same genuine removal path an unmount already exercises.
- **The sky dome (roadmap item 6) is a real Three.js mesh with a horizon-discard shader, not the MapLibre-sky fallback the plan also scoped as a go/no-go alternative.** `src/map/skyDome.ts`: `RADIUS_M = 120_000`, `renderOrder = -1` (drawn before the network), `depthWrite: false`/`depthTest: false` (never touches or reads the depth buffer). The fragment shader discards every point at or below the local ENU horizon plane (`vLocal.z <= 0.0`) rather than attempting real depth interop with MapLibre's tiles — the same class of deliberate sidestep as F3.2's opacity-based underground mode, and explicitly named as such in the file's own doc comment (§3A.4 is the open-ended depth-interop problem both features avoid). Its verified-clean envelope, from the go/no-go gate (pitch 0/45/70 × noon/02:00): only the two pitch-70° cells actually exercise the horizon discard (pitch 0/45 draw nothing to wash in the first place, so they pass vacuously) — and there's a real zoom-clipping interaction, unrelated to this feature: MapLibre v6 computes the custom-layer far clip plane dynamically from visible horizon distance, and it shrinks below the dome's fixed 120 km radius at close zoom, which a first pass of this work misread as a sky-dome bug before isolating it via git-stash A/B as pre-existing MapLibre behavior. Net effect: the dome's real envelope is roughly "pitch ≥70° at zoom ≤12.5" — worth knowing before assuming it's visible from every camera pose. `verify:mvp7` check 10 asserts the mesh criteria (`renderOrder < 0`, disabled depth write/test) directly against the real scene.
- **Auto-underground (roadmap item 5's last piece) decides on the followed vehicle's real ALTITUDE, not its track segment's structure tag — deliberately.** `src/map/autoUnderground.ts`'s `decideAutoUnderground` is a pure function (no store, no map, no DOM) fed the vehicle buffer's `LANE_Z` for whichever run is followed. A track point tagged `underground` can legitimately sit well above nominal depth mid-ramp (see the MVP 6 gradient-limiting notes above — only the altitude channel moves during ramping, the structure tag doesn't), so "is this point tagged underground" and "does this look underground to a viewer" are different questions, and the second one is what a view-mode switch should answer. Altitude is already in the vehicle buffer with zero extra track lookup needed on the frame path (§3A.7 compliance). Engages below −5 m, releases above −1 m — the 4 m gap is a hysteresis band, not a rounding margin: a single shared threshold would flicker the whole basemap every time a train's altitude oscillates near a portal. A manual toggle mid-follow marks `overridden: true` and auto stands down for the rest of that follow session, so auto never fights a user who explicitly wants a different view. Two small, disclosed gaps in the state machine, inherited from the brief's own design (not found-and-left by the implementer): (1) toggling underground ON before the engage threshold then OFF after crossing it doesn't register as an override, since `prev.auto` was `false` at toggle time — auto can silently re-engage on the next altitude sample; (2) if the followed run disappears from the vehicle buffer entirely (trip ended) while still following, altitude reads `null` and an already-auto-engaged state can stick until `following` is explicitly cleared. Neither is exercised by `verify:mvp7` checks 8-9.
- **Two new preprocessor gates, both hard-fail (the build stops with a clear message), not soft warnings — this is their disclosure mechanism.** (1) `check_track_gradient` (`rust-engine/preprocessor/src/main.rs`, Task 1) rejects any consecutive track-vertex pair steeper than `MAX_TRACK_GRADIENT` (4%, the same ruling gradient `tools/trackProfile.mjs`'s `limitTrackGradient` already enforces client-side) — closes the exact defect class that shipped as MVP 6's "vertical wall at a portal" bug (108% grade, found by a human, not a gate) by making it impossible to reach `network.tmb` at all. (2) A closed bypass in the pre-existing snap-distance gate (`MAX_SNAP_M`/`SNAP_WARN_M`): Task 2's Step 1 finding, worth stating precisely since it's easy to get subtly wrong by summarizing from memory — **the pre-existing gate never actually fired for Mo Chit's 187.4 m pre-fix defect**, because it only ever checked GTFS's own raw stop coordinate against the track, never `network.json`'s hand-patched `station.position` — and Mo Chit's error was entirely IN that hand-patched position (a citation to an untagged OSM node ~270 m from where it was used to justify), a case the gate structurally could not see. Task 2 closed this by adding a third validation block that checks registry station positions for GTFS-simulated lines too, not just the GTFS coordinate. Both gates are unit-tested with synthetic fixtures (`gradient_gate_rejects_a_portal_wall`, `gradient_gate_accepts_a_ruling_grade_ramp`, etc. in `main.rs`) rather than only exercisable via a live Overpass fetch.
- **`npm run verify:legibility` (Task 11) is a real, currently-failing gate — read the number before assuming "night legibility" is solved.** It samples real lit deck pixels (`MeshLambertMaterial`, not the unlit `LineMaterial` centerline drawn 0.6 m above the same polyline — a first pass of this harness structurally always hit the wrong geometry and was caught and rewritten before landing) at a tight per-line zoom (z18/z19, one pose per line since no single global pose fits all 12 lines that tight), computing WCAG contrast against the basemap at noon and 02:00. **14 of 20 line/time samples fail** the real WCAG floor (`MIN_CONTRAST = 3.0`, not weakened): **9 of 10 simulated lines fail at night** (only Airport Rail Link passes both times); at noon, Sukhumvit/Yellow/Gold/Red Light/Blue also fail. This is materially bigger than the MVP 6 Task-14 note ("night theme made all lines invisible... fixed") suggested was still true — that fix raised a floor, it didn't make the network broadly WCAG-legible. MRT Blue's failure is specifically traced to 8-bit sRGB colour quantization saturating its `#1964B7` livery near-black at night regardless of the ambient floor — not fixable by another `sun.ts` floor tweak; the other 8 failing lines may have more headroom. Left failing on purpose, same precedent as `verify:perf`'s `>=300` gate — a follow-up task (not MVP 7) should fix the underlying shortfall with a per-material minimum-brightness mechanism.
- **Eco mode's steady-state throttle is a clean, exact 1 render/second — but only after a brief settle window.** Measured directly (not just trusted from the `ECO_TICK_MS = 1000` constant): monkey-patching `NetworkLayer.render()` to count invocations shows a one-time burst of repaints in roughly the first second after `ecoMode` flips true (MapLibre's own internal repaint activity settling — tile/symbol state — not this app's throttle), after which the count is dead flat at +1/second. A verify harness measuring from the moment eco mode is enabled will see this transient and can misread a correctly-throttled loop as unthrottled; `verify:mvp7` checks 11-12 wait 1.5 s before starting their measurement window for exactly this reason.
- **A registry-drift lesson for whoever plans the next slice of work: ad-hoc mid-plan tasks are real and expected, and a downstream task's brief can go stale between when it's written and when it executes.** The Orange East+West merge (see the correction note earlier in this file) landed between Task 3 (which added `orange-west` as its own entry) and Task 12 (this section) — Task 12's own brief still assumed the pre-merge 13-line/`orange-west` shape and had to be corrected against the real registry before its acceptance harness could be written. `npm run verify:mvp7` documents this correction in its own header comment, not just here.

## Implementation notes (MRT Blue weekend calendar split, 2026-08-08)

- **A user-reported "the MRT timetable looks duplicated" bug traced to a genuine gap in the upstream Namtang GTFS feed, not this codebase's engine or preprocessor.** `calendar.txt` has **no Saturday-only or Sunday-only service anywhere in the whole feed** — every one of its service rows is weekday(Mon-Fri), all-7-days, or one combined Saturday+Sunday block. MRT Blue (`gtfs_route_id "3"`) nonetheless publishes 15 trips with genuinely different Saturday vs. Sunday variants — distinct headsigns, sometimes distinct destinations (e.g. "Tao Poon (Saturday)" vs. "Tao Poon (Sunday and Public Holiday)" both terminating differently) — but Namtang assigned every one of them to that single shared Sat+Sun calendar entry instead of splitting it. By strict GTFS semantics that makes both variants "scheduled" on every weekend day at once, which is exactly the symptom: a station board on a real Saturday showed Sunday-only headsigns interleaved with the Saturday ones at the same arrival second. The engine's calendar resolution (`sim-core/src/calendar.rs`'s `service_active_on`) is textbook-correct GTFS; there was nothing to fix there.
- **Fix: `day_qualified_service_split` in `rust-engine/preprocessor/src/main.rs`** synthesizes a restricted single-weekday `ServiceDoc` from a trip's own headsign — but only when both conditions hold: the headsign ends with one of exactly two known suffixes (`" (Saturday)"` / `" (Sunday and Public Holiday)"`, the only two phrasings found anywhere in the feed), **and** the trip's underlying service is precisely the ambiguous Saturday+Sunday combination (`weekday_mask` has both bits set). Verified narrow before writing the fix, not assumed: a full-feed scan found this pattern on exactly 17 trips, all under route `3` (MRT Blue), nowhere else. Synthetic services are memoized per `(original_service_idx, day_bit)` so every trip sharing a split reuses one `ServiceDoc` rather than minting a duplicate per trip (`services` grew from 3 to 5 in the committed report — two new entries, not fifteen).
- **Two of those 17 trips (5272, 7865) have a day-qualified headsign but sit on an unrelated plain weekday-only service** — a separate, smaller labelling oddity in the same feed, most likely an upstream mistake, but not the cause of any duplication (they just run Mon-Fri under a normal single calendar with a confusing headsign). `day_qualified_service_split`'s second condition (the service must actually be the ambiguous Sat+Sun combo) deliberately leaves these two alone rather than guessing intent the calendar data doesn't support — same standing practice as the Mo Chit/Itsaraphap snap fixes: verify before rewriting, never invent a position (or, here, a service day) the source doesn't actually assert.
- **A real, previously undetected side effect: the bug was inflating measured weekend peak concurrency.** Before the fix, `public/data/network.report.json`'s `peak_concurrent_weekend` was **212**; after, it's **173** — both Saturday- and Sunday-intended MRT Blue runs were being simulated simultaneously on every weekend day, roughly double-counting that line's weekend vehicles. The **weekday** peak (`peak_concurrent`, 246) is untouched — none of the 17 affected trips ever ran on a weekday service, confirmed by diffing the regenerated report against the committed one (every other field — `runs` at 8193, every `per_route` entry, snap warnings — is byte-identical; only `services`, `peak_concurrent_weekend`, and the feed-refetch bookkeeping fields changed). §5's NF1 status note and any future citation of "weekend peak 212" should be read as **173** going forward.
- **Regenerating `network.tmb` required a fresh `npm run data:fetch-gtfs` pull, not the already-extracted `.gtfs-cache`** left over from an earlier session — that older snapshot had an unrelated ragged CSV row in `routes.txt` (BTS Sukhumvit's row was missing a field, shifting `route_color` out and tripping the preprocessor's own pre-existing `bad route_color ''` validation). Confirmed unrelated to this fix by inspection before working around it: nothing in `day_qualified_service_split` touches route or colour parsing. A fresh pull (`feed_version` 20260803 → 20260807) preprocessed cleanly.
- **A debugging note for whoever next needs to point a dev server at a specific worktree: `npm run dev` silently falls back to the next free port (5174, 5175, …) if 5173 is already taken by a stale server from another worktree/session, and a hardcoded `http://localhost:5173/` in a verify script then silently tests the WRONG instance** — it doesn't error, it just serves stale data with no indication anything is wrong. This produced a real false-negative during this fix's own verification (a "still broken" result that was actually testing an old build). Check `netstat -ano | grep LISTENING` on the 517x range before trusting a live-browser check that contradicts an otherwise-clean unit-test pass.

## What this project is

Greater Bangkok Metro Mini 3D is a web-based 3D visualization of Bangkok's rail transit network (BTS, MRT, SRT, Airport Rail Link), inspired by Mini Tokyo 3D. Trains are placed on 3D track by **interpolating static GTFS timetables** — there is no live vehicle feed (GTFS-Realtime is explicitly out of scope for v1.0). The app lets a user scrub to any past/future time and see where trains *should* be per schedule.

## Planned architecture (from the SRS)

The system is three layers plus an offline pipeline:

1. **Data pipeline** (`tools/gtfs_preprocessor/`, Rust CLI) — converts a GTFS ZIP feed into a compact binary cache (target: **< 3 MB compressed**), falling back to OpenStreetMap geometry where `shapes.txt` is coarse or missing. This is offline/build-time only; scraping (if ever used as a fallback) belongs here, never in client runtime.
2. **Simulation core** (`rust-engine/`, Rust → WebAssembly via `wasm-pack`) — parses the binary cache and computes vehicle kinematics. Runs inside a Web Worker, decoupled from the render frame rate (fixed-timestep sim tick; render side interpolates between the two latest sim states).
3. **Frontend** (`src/`, Vite + TypeScript + React 19 + Tailwind + Zustand) — MapLibre GL JS base map with a custom `CustomLayerInterface` WebGL layer that hosts a Three.js scene for 3D track/train rendering.

### Load-bearing design decisions (SRS §3A) — do not casually deviate

- **Worker↔main-thread transfer:** use **transferable `ArrayBuffer`s** via `postMessage`, not `SharedArrayBuffer`. Avoids the COOP/COEP cross-origin-isolation requirement entirely (many static hosts, e.g. GitHub Pages, can't set those headers). Only reconsider `SharedArrayBuffer` if profiling proves transfer overhead matters, and only after confirming header support on the deployment target.
- **Wasm↔JS API shape:** the engine should expose "tick(time) → fills a shared flat `Float32Array`" (one buffer, zero-copy read), not per-vehicle getter calls — the JS↔Wasm boundary crossing, not the math, is the actual bottleneck against the 3 ms/frame budget.
- **Rendering:** use Three.js `InstancedMesh` per vehicle type (one draw call per type), not one mesh per train.
- **Coordinate precision:** adopt a floating-origin / camera-relative coordinate scheme from the start (MVP 1), not as a retrofit — absolute mercator coordinates at city scale cause visible `float32` jitter, especially in follow-camera.
- **MapLibre↔Three bridge:** both must share the *same* WebGL context (don't let Three create its own canvas). Positions go through `MercatorCoordinate.fromLngLat()`; depth/occlusion between MapLibre terrain and the Three layer is the hard part of underground transparency (F3.2) — budget real time for it. `deck.gl` + `MapboxOverlay` is the documented fallback if the bridge becomes a time sink.
- **State ownership:** Zustand holds only UI-derived state (selected train, line filters) — per-frame kinematics must never enter React state, or re-renders thrash.
- **Serialization:** evaluate `rkyv` (zero-copy deserialization) for the binary cache before falling back to Bincode. Reserve MessagePack/Protobuf for any interchange boundary that isn't Rust-to-Rust.
- **Track geometry:** 3D coordinates `[lon, lat, altitude_meters]`; altitude by structure type — underground −12 to −25 m, at-grade +0.5 m, elevated +12 to +22 m. Apply Catmull-Rom/Bézier spline smoothing so curve nodes don't produce abrupt heading changes.
- **Motion model:** status per vehicle at time *t* is dwell / in-transit / inactive based on scheduled arrival/departure times; in-transit progress uses the smoothstep ease `3p² − 2p³` for accel/decel, with heading derived from the track's 3D tangent (see SRS §F2.1–F2.2 for the exact formulas).

## Delivery model — build in this order

The project is scoped as **vertical MVP slices**, not horizontal layers (data → engine → UI). Each MVP is a complete, demoable increment; later MVPs assume earlier ones are done. If asked to implement a feature, place it in the right MVP rather than building ahead of it:

1. **MVP 1 — Green Line track only.** ✅ **Done.** App shell, MapLibre base map, Three.js bridge + floating-origin coordinates, Green Line 3D geometry rendered, free-camera orbit. 2. **MVP 2 — Green Line data pipeline.** Rust CLI GTFS→binary cache (Green Line only), client-side load/validation, stop-snapping, calendar resolution. Still no motion.
3. **MVP 3 — Green Line trains moving.** Wasm interpolation engine, Web Worker + transferable-buffer transport, `InstancedMesh` trains, basic time-warp (1×/5×/10×/60×).
4. **MVP 4 — Interaction & UI.** Follow-camera, station/vehicle inspector, time scrubber, live timetable drawer. Still Green Line only.
5. **MVP 5 — Multi-line breadth.** ✅ **Done.** Generalized to line-agnostic code; added Purple, ARL, Pink, Yellow, Gold, SRT Dark/Light Red (9 lines total, 155 stations, 4,481 runs).
